# PQTG key schedule (wire `3.1`, `relay-4`)

*Normative for the v3 gateway handshake and the relay. Introduced 2026-09-12
(backlog B2, structured domain separation; B3, keyed chaining KDF). Implemented
in `src/kdf.rs`, used by `src/crypto.rs` (v3) and `src/relay.rs`. Pinned by
`tests/kdf_kat.rs` against vectors generated by an independent implementation
(`tests/vectors/gen_kdf_vectors.py`, Python `hashlib` + `hmac`).*

## 1. Primitives

| Symbol | Definition |
|---|---|
| `SHA3(x)` | SHA3-256 (FIPS 202), 32-byte output |
| `HMAC(k, m)` | HMAC-SHA3-256 (RFC 2104 over SHA3-256), `k` is 32 bytes, 32-byte output |
| `len ‖ x` | big-endian u32 byte length of `x`, then `x` |
| `be32(n)`, `be64(n)` | big-endian encodings |

Every part of every hash input is length-prefixed, fixed-size parts included,
so the encoding is uniform and no two part sequences can produce the same
byte string.

## 2. Domain tree (B2)

Each hash and PRF use has a 32-byte domain constant `D[path]`, derived from a
path in one tree, after Rosenpass's `hash_domain_ns!`:

```
D[]               = SHA3("PQTG-DOMAIN-TREE-v1")
D[parent / leaf]  = SHA3(D[parent] ‖ be32(len(leaf)) ‖ leaf)
```

Two paths cannot share a constant without a SHA3-256 collision; the length
prefix on each leaf keeps `a/b`, `ab` and `a` `b` apart. Every path in use is
registered in `src/kdf.rs::ALL_DOMAINS`, checked for distinctness by a unit
test, and published with its constant in `tests/vectors/kdf-domains.json`:

| Path | Use |
|---|---|
| `gateway/v3/transcript` | v3 handshake transcript, signed by the server |
| `gateway/v3/client-hello` | v3 ClientHello digest, signed by the client |
| `gateway/v3/chain` | start of the v3 session-key chain |
| `gateway/v3/mix/kem` | chain step: ML-KEM-768 shared secret |
| `gateway/v3/mix/qkd` | chain step: ETSI 014 key bytes (Hybrid only) |
| `gateway/v3/mix/transcript` | chain step: transcript |
| `gateway/v3/session-key` | chain output |
| `relay/v4/hello` | RelayHello digest, signed by the client |
| `relay/v4/transcript` | relay transcript, signed by the server |
| `relay/v4/key/c2s`, `relay/v4/key/s2c` | directional record keys |
| `relay/v4/ratchet` | one record-layer ratchet step |

Adding a domain means adding a path to the registry and a line to the
vectors; nothing else is shared.

## 3. Constructions

```
hash(D, p1, …, pn)   = SHA3(D ‖ len ‖ p1 ‖ … ‖ len ‖ pn)          public data only
prf(k, D, p1, …, pn) = HMAC(k, D ‖ len ‖ p1 ‖ … ‖ len ‖ pn)        k is a secret
```

A running chaining key (`src/kdf.rs::Chain`, Noise style):

```
start(D)            ck  = hash(D)                 = SHA3(D)
mix(D_step, x)      ck' = prf(ck, D_step, x)
finish(D_out)       out = prf(ck, D_out)
```

Each step is a PRF keyed by the previous chaining key, so the order and the
count of the inputs are bound, and mixing the same inputs in another order
gives another key. The chaining key is zeroized when the chain is consumed.
Secrets never enter a bare hash: `hash` is for public data, `prf` and `Chain`
for anything secret.

HMAC-SHA3-256 was chosen over keyed SHAKE256 because it is the standard PRF
construction over the hash this project already standardises on, and the
RustCrypto `hmac` crate is pure Rust on the same `digest` line as `sha3`.
Mixing a QKD key through a PRF is computationally secure; it does not
preserve the information-theoretic security of the QKD key, and no claim of
that kind is made for a derived key.

## 4. Gateway v3 (wire `3.1`)

Inputs: `cr`, `sr` (32-byte randoms), `ek` (ML-KEM-768 encapsulation key),
`ct` (ciphertext), `svk` (server Falcon-512 vk), `cvk` (client Falcon-512
vk), `slh` (client SLH-DSA vk), and the fields of `PROTOCOL-V3-QKD-KEYID.md`.

```
hello_digest = hash(D[gateway/v3/client-hello],
                    cr, be64(timestamp), ek, cvk, slh,
                    be64(requested_key_size), client_sae_id, [qkd_capable])
                 signed by the client (Falcon-512) as ClientHello.hello_sig

transcript   = hash(D[gateway/v3/transcript],
                    cr, sr, ek, svk, ct,
                    [key_mode],            0x01 Hybrid, 0x00 PqcOnly
                    qkd_key_id,            empty in PqcOnly
                    master_sae_id,
                    be32(qkd_key_len))     0 in PqcOnly
                 signed by the server (Falcon-512) as ServerHello.transcript_sig

ck           = start(D[gateway/v3/chain])
ck           = mix(D[gateway/v3/mix/kem], kem_ss)
ck           = mix(D[gateway/v3/mix/qkd], qkd_bytes)       Hybrid only
ck           = mix(D[gateway/v3/mix/transcript], transcript)
session_key  = finish(D[gateway/v3/session-key])
```

PqcOnly and Hybrid differ by a whole chain step, so no PqcOnly key can equal
a Hybrid key. The transcript step binds the key to the negotiated mode, the
ETSI 014 `key_ID`, the master SAE-ID and the QKD key length, all of which are
under the server's signature. Wire `3.0` (flat labels `pqtg-transcript-v3`,
`pqtg-session-v3`, v2 `mix_keys` combiner) is not kept; a `3.0` peer and a
`3.1` peer do not derive the same key. The v2 schedule (`transcript_hash`,
`mix_keys`, `derive_session_key`, flat `pqtg-*-v2` labels) and the identity
fingerprint (`pqtg-identity-fingerprint-v1`) are deliberately unchanged: the
KirQ Phase 1 client speaks v2, and pins must keep their values.

Vectors: `tests/vectors/handshake-v3.json` (transcript in both modes, hello
digest, session key in both modes).

## 5. Relay (`relay-4`)

```
hello_digest = hash(D[relay/v4/hello], cr, be64(timestamp), ek, cvk, slh)
                 signed by the client as RelayHello.hello_sig

transcript   = hash(D[relay/v4/transcript], cr, sr, ek, ct, cvk, svk)
                 signed by the server as RelayServerHello.transcript_sig

k_c2s        = prf(kem_ss, D[relay/v4/key/c2s], transcript)
k_s2c        = prf(kem_ss, D[relay/v4/key/s2c], transcript)

k(n+1)       = prf(k(n), D[relay/v4/ratchet], be32(n+1), fresh)
                 fresh = ML-KEM-768 shared secret from the COMMIT_KEM record,
                 or empty on a COMMIT_HASH_ONLY step; k(n) is zeroized after
```

The two directional keys come from the same secret under different domains,
so they are independent PRF outputs and the two directions can never share a
key or a nonce stream. Each ratchet step is keyed by the current epoch key,
so epoch `n` cannot be recovered from epoch `n+1`, and a KEM step binds fresh
material an attacker holding `k(n)` does not have (post-compromise security
across that boundary, `formal/RATCHET-RESULTS-2026-09-12.md`). `relay-3`
(hash-only labels) is not kept; a `relay-3` peer is refused at the version
check.

Vectors: `tests/vectors/relay-v4.json` (hello digest, transcript, both
directional keys, a hash-only step and a KEM step).

## 6. Formal models

The Verifpal models under `formal/` abstract every derivation as a one-way
function of its inputs with distinct label constants; they do not depend on
the concrete constants or on keyed versus unkeyed hashing. This change keeps
the same secrets entering the same derivations in the same order, so the
symbolic shape is unchanged and the 2026-09-12 results stand for `3.1` and
`relay-4`. The vectors are what tie the models to the code.

## 7. Regenerating the vectors

```
python3 tests/vectors/gen_kdf_vectors.py      # rewrites the three JSON files
cargo test --test kdf_kat
```

The generator is deliberately a second implementation from this document,
not a port of `src/kdf.rs`. A deliberate change to any rule above must change
the wire version, this document, the generator, and the vectors together.
